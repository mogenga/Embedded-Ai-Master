## 3. Ontology 的三种落点

"Ontology"在讨论中被混用为多种形态,它们与实验的关系完全不同:

| 落点 | 形态 | 与对照实验的关系 |
|---|---|---|
| **E1. 领域本体 / 知识图谱检索** | 显式建模实体(芯片/外设/寄存器/错误码/症状/原因/测试)与关系,查询时做实体识别 + 图遍历,产出候选文件 | **形态上可比,但需另设设计**(§4、§5) |
| **E2. GraphRAG 式自动抽取** | LLM 从 KB 自动抽实体关系 + 社区摘要 | E1 的工程化变体;构建与重建成本高,建议等 E1 有信号再评估 |
| **E3. 本体作为确定性事实层** | 寄存器位含义、错误码解码、引脚复用等结构化事实 | **不应进本实验**。按 todo §6.2 约束 1,这类事实永远由工具返回、不靠检索;本实验只测"第一跳怎么找到对的文件" |
| **E4. 本体做 KB 一致性门禁** | 校验症状文件引用的寄存器/错误码是否存在于 reference、厂商型号是否闭合、触发词是否覆盖 | **另一条赛道**。属 R5/R6 质量门禁的强化,不参与检索指标;投入产出比在 103 文件规模下最确定 |

**E3 与 E4 不是"被排除",而是"问的不是同一个问题"**:本实验的立项目的是关闭决策点 #2(KB 三级渐进加载的载体),要回答"第一跳该读哪个文件"。E3 回答"这个 bit 是什么",E4 回答"KB 自身是否自洽"。

## 4. 为什么不能与 A/B/C/C′ 同表比较

A/B/C/C′ 可比的**判据不是机制相似**,而是共享同一个评测框架:同一份语料、同一批 gold、同一种输出形态(候选文件排序)、同一套指标。B 虽是工具循环,已在 todo §6.1 为它单列"最终推荐候选集"计分口径,仍在框架内。

把 Ontology 放进去会同时引入四个混淆项:

1. **构造泄漏**:本体若从同一份 KB 抽取,等于把"哪个文件是答案"编码进结构;不做数据切分,无法区分增益来自检索能力还是泄漏。
2. **成本不对称**:A/B/C/C′ 是零 schema 成本;不把建模工时与 KB 变更后的同步成本计入,比较没有意义。
3. **查询分布不匹配**:现有 274 条查询(172 index + 102 search)是单跳"找对文件"任务;本体的强项是多跳/关系型查询。用单跳测必然低估,补多跳又等于另一个查询集。
4. **输出形态**:本体的自然输出可能是结构化答案(如 bit 位),与现有 Recall@2 / Hit@1 / MRR / nDCG 不兼容。

另有一个容易被忽略的事实:现有 KB 的四段式症状文件(其核心是"症状 → 原因 → 测试表")+ `index.yaml` 症状索引 **本身就是一层轻量本体**。E1 的增益必须相对这层既有结构来测,不能把"把 KB 改写成图谱"当作从零开始的收益。

## 5. 若将来纳入,需要补齐什么

按 todo §6.2 实验约束 4(R9 评测公正性)的同一原则,缺一不可:

| 项 | 内容 |
|---|---|
| 方案定义 | E1 的实体/关系范围、查询链路;输出必须仍是"候选文件 + 排名",才能进同一套指标 |
| 新增假设 | H8:多跳查询下 E1 的 Recall@2 是否高于 C′;H9:单跳查询下 E1 是否不劣于 C′ |
| 查询集 | 补 30-50 条多跳查询,gold = 相关文件集;与主查询集分开报告,不混算 |
| 成本指标 | 本体建模工时、KB 变更后的同步/重建成本、查询侧实体识别延迟 |
| 泄漏控制 | 本体抽取与评测集切分,禁止用 gold 标注反向构造本体 |
| 判定标准 | **先固化再跑**:E1 仅在多跳子集显著优于 C′ **且**维护成本可接受时才进入候选 |

主实验的判定表(引入向量召回 / BM25 上位 / 规模阈值 / 退夜批 / 查询归一化 / 置信阈值)不因本文件改变。

## 6. 与既有约束的关系

- **R3 工具必须诚实** 与 todo §6.2 约束 1:确定性事实进工具,不进检索。E3 归 M2 领域层 MCP 工具,单独验证。
- **BR-3 三级渐进加载结构不变**:索引 → 症状文件 → reference。E1 若纳入,只能替换"第一跳"的检索实现,不能改动加载结构。
- **R5/R6 质量门禁**:E4 可并入此线,作为 KB 一致性审计手段;它是质量工程,不是检索选型。
- **R9 评测公正性**:任何新方案进表前,判定标准与评测集构造规则先固化。

## 7. 重启条件

满足任一即重新评估:

1. 主实验(H1-H7)完成且决策点 #2 关闭,知识层接口形态确定后再考虑增强;
2. 真实诊断中出现**多跳检索**的明确失败案例(单跳能命中,但需要跨文件关系推理),且现有 KB 结构无法通过四段式表补足;
3. KB 规模或结构复杂度增长到 `index.yaml` 关键词路由与文件级阅读难以为继;
4. E4(一致性门禁)在实践中证明本体建模成本可接受——说明 schema 已有现成投入,可顺带评估 E1。
