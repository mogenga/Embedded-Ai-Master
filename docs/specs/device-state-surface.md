## 0. 结论先写

1. **不做面板，也不复活 `getBoardState`。** 设备状态继续由**工具行的输出**与
   `device_status` 事件承载。
2. **BR-6 验收①「设备面板实时反映工具结果」按字面已作废**，改写为
   「工具结果本身即设备状态的可读出口」。理由见 §2，这是 2026-10-26 删面板那次
   决定的直接后果，不是新决定。
3. `device_status` 事件**保留**，定位从「面板的数据源」改成「结构化留痕」。它现在
   没有 UI 消费者，这是**有意**的，不是死代码——判据见 §4。

## 1. 现在设备状态从哪来、到哪去

### 生产者

`mcp-servers/probe/tools.ts` 的每个工具在成功结果里附一个 `deviceStatus`：

```ts
const deviceStatus = (): DeviceStatus => active?.status() ?? EMPTY_STATUS;
```

`DeviceStatus`（`mcp-servers/probe/backend.ts:34`）只有四个字段：

| 字段 | 取值 | 含义 |
|---|---|---|
| `backend` | `renode` / `openocd` / `none` | 哪个后端在跑 |
| `probe` | `attached` / `detached` | 探针是否连着 |
| `cpu` | `halted` / `running` / `unknown` | 目标是否停住 |
| `serial` | `open` / `closed` | 串口是否开着 |

**它不知道板卡型号、不知道端口、不知道工作区。** 这一点决定了「面板」能画的东西
其实只有四个状态词。

### 内核

`src/loop/query.ts:432` 的 `appendDeviceStatus`：工具成功且带 `deviceStatus` 时，
在 `tool_result` 之后追加一条 `device_status` 事件；形状不合法时改追加一条
`status{status: "device_status_invalid"}`。两条都 `parent` 指向那次调用。

### 渲染器

`desktop/renderer/protocol.js:834` 把它原样透出成 `{ type, device, server, tool, updatedAt }`。
`desktop/renderer/app.js:3290` 的 `case "device_status"` **刻意什么都不画**，注释写明
「工具自己那一行与输出就是现在报告设备的方式」。

### 真实数据

本机 3 个真实会话，**0 条 `device_status` 事件**（都是 KB / `ls` / `shell` 调用）。
也就是说这条链路在真实使用里**还没有被走过**——它只在 probe 工具被调时出现。

## 2. BR-6 验收①还成立吗

BR-6 原文（`docs/BRD.md:184`）：

> ① 设备面板实时反映工具结果；② 页面重载后状态从会话日志完整重建；③ 实现形态依 harness 的 client 插件/前端扩展机制选型

验收①的**前提是「有一个设备面板」**。那个面板（Board 页签）已在 2026-10-26 按用户
决定整体删除（D-193），`SUPPORTED_PANES` 现为 `file` / `artifact` / `serial`，
全仓 `getBoardState` 零命中。

于是有两条路，本文选 **(a)**：

| 选项 | 内容 | 判定 |
|---|---|---|
| **(a)** | 承认验收①随面板删除作废；BR-6 收敛为「从日志重建转录」一条（验收②） | **选这个** |
| (b) | 把「实时反映工具结果」改由工具行承载，视作已满足 | 部分成立但不完整，见下 |

**为什么 (a) 而不是 (b)**：「实时反映」在 (b) 里确实成立——工具行是实时的，
`device_status` 也随每次调用更新。但 BR-6 要的是「**一眼看到**当前状态」，而
工具行是**流水账**：要回答「现在探针连没连、CPU 停没停」，得往前翻到最近一次
probe 调用。把那叫「满足验收①」是在偷换「面板」与「日志」。

所以按 R3 的同一逻辑：**做不到的事就说做不到**，把验收改写清楚，不留一条
看起来已完成、实际没人兑现的条目。

### 这条改写需要谁点头

它是里程碑验收口径的变更，不是实现选择。**已记入本文与 BACKLOG，供用户复核**；
BRD 原文不动（BRD 是历史需求文档，改它会让过去的决策失去上下文）。

## 3. 不复活 `getBoardState`（具体约束）

D-193 的教训是一句可复用的话：**不要画一个需要扫描器才能填的面板。**

具体到这条：

- `getBoardState` 是浏览器形态时代的命令，它要的是一个**工作区扫描结果**
  （板卡型号、端口、工程文件）。内核从来没有这个能力，Host 也从来没有实现过它。
- 现在设备状态的唯一来源是探针自己的 `DeviceStatus`，四个字段。
- **任何新界面都不得引入 `getBoardState` 这个名字**，也不得为了填面板去发明
  「板卡扫描」。`grep getBoardState` 必须一直是 0 处。

### 将来若要面板，前置条件是

1. **有真实需求**：出现「操作者反复问现在连没连 / 停没停」的实测，而不是
   「BRD 里写了面板」。
2. **数据来自已存在的事实**：只能画 `DeviceStatus` 的四个字段 + 最近一次
   probe 调用的时间。不得引入扫描器。
3. **形态先定**：面板 / 顶栏 chip / 工具行徽标，三种选一个并写决策记录——不直接
   开工。
4. **`device_status` 的消费者要能被回放截断**：面板若上线，它必须和转录一样接受
   `atSeq`（9.2 已经建立了这个约定：`sessionLoadedEvent` 是唯一的截断入口）。
   回放到第 3 条却显示第 40 条的状态，是同一个错的另一种写法。

## 4. `device_status` 事件：保留，还是死代码

**保留，定位是「结构化留痕」**。判据：

| 反对「死代码」的证据 | 说明 |
|---|---|
| 它有**真实生产者** | probe 的每个成功工具调用都会带，不是零生产者 |
| 它有**投影出口** | `protocol.js:834` 把它转成结构化对象，不是被丢弃 |
| 它记录的东西**工具行文本里没有** | 工具输出是给人看的字符串；`device_status` 是四个枚举字段，机器可读 |
| 夜批管线将来会用到 | BR-7 要判「每轮产出证据」，`device_status` 是「这轮到底连上没连」的机器可判来源（目前 `nightly-batch.mjs` 还没消费它，是已知的下一步） |

**但「保留」不等于「已验证」**：本机 3 个真实会话里 0 条该事件，这条链路
在真实使用中**还没被走过**。这一点必须如实写着。

### 触发重新审视的条件

- 夜批管线接入它，或
- 出现「操作者问当前状态」的实测，或
- 内核决定删除它（那时 `protocol.js` 的 case、`MATRIX.md` 的那一行、本文
  §4 要一起改）。

任何一个触发之前，它保持「有生产者、有投影、无消费者」这个状态，**不删**。

## 5. 与 BR-6 验收②的关系

验收②「页面重载后状态从会话日志完整重建」**已经落地**：`session_loaded` 从日志
重建整条转录（含工具行）。所以 BR-6 收敛后剩下的这一条是可验证的，有测试钉住。

> **2026-11-09 更正**：9.2 曾按 `atSeq` 加过一个可拖动的事件回放条，**用户在同一天
> 要求移除**（"顶部事件回放功能不要"）。删掉的是控件与渲染层状态；`sessionLoadedEvent`
> 的 `atSeq` 参数保留（`forkSession` 与子代理只读视图依赖它）。所以现在 BR-6 剩下的
> 是「打开会话即从日志重建」，**不再包含「停在任意中间位置」这层能力**。
