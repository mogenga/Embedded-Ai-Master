## 1. 业务背景

### 1.1 目标问题

嵌入式固件调试是高知识密度、强工具依赖的活动,当前存在四个结构性痛点:

1. **症状先行,根因难求** — 开发者看到的是"串口乱码""上电无输出""间歇死机"等表象,根因可能藏在时钟树、竞态、DMA、电源、厂商独有陷阱等数十个假设里。
2. **经验不可迁移** — 每家 MCU 厂商都有独有名坑(ESP32 strapping、Kinetis WDOG 默认开、AVR 熔丝写 0=使能……),散落在官方手册、论坛与个人经验里;新手反复踩,专家经验无法沉淀复用。
3. **工具链割裂** — 探针、串口终端、逻辑分析仪各管一段,缺少"从症状到根因"的结构化推理层;确定性事实(寄存器位含义、错误码表)与因果推理(为什么乱码)混作一团。
4. **AI 缺位** — 商业仪器与调试器厂商(Saleae/Keysight/Segger)均无 AI 调试功能(2026-10 调研核实);开源先例只有工具封装,缺知识推理层。

### 1.2 先例与学术依据(为什么这样做)

调研三个最接近的开源先例(embeddedskills ~730★ / embedded-debugger-mcp ~198★ / jlink-mcp ~32★)与三篇诊断类论文,收敛出七条设计结论(已转化为本文 §8 硬性业务规则):

1. 确定性事实进工具,因果推理进知识文件 + LLM;
2. 症状→原因→测试表是核心结构(非刚性故障树),LLM 灵活对表推理;
3. 三级渐进加载(索引摘要 → 症状正文 → reference 表),按需读,上下文不爆;
4. 不用向量 RAG — **注意:此为推理结论,实测对照实验已立项**,见 §14;
5. KB 写"交互脚本" — KB 从百科变成 agent 执行的协议;
6. 工具必须诚实;
7. 专家优先路由(确定性检查表置信度够直接答,LLM 处理新颖症状)。

学术佐证:人机协作结构化流程把 LoRa bring-up 成功率 25%→100%(arXiv:2307.03817);信息增益最大化的澄清提问驱动诊断循环(arXiv:2605.05386)。

## 2. 产品定位

### 2.1 一句话定位

面向嵌入式开发者的**症状驱动固件调试 agent 平台**:用户报症状,agent 用探针工具取证 + 知识库推理,定位根因并给出**可证伪的**修复建议。

### 2.2 两层结构(2026-10-15 方向变更后)

| 层 | 定位 | 内容 |
|---|---|---|
| **平台层(harness)** | 领域无关的 agent 框架 | 模型接入、上下文、工具、会话、权限、扩展机制 |
| **领域层(嵌入式调试)** | 以 MCP/插件/Skills 形式接入的领域能力 | 探针取证、知识库、诊断 UI、验证管线 |

> **方向变更说明(2026-10-15)**:原方案基于 dsh(DeepSeek Harness)二次开发;现改为**独立开发底层 agent 框架**,平台层与领域层并行全新建设。**v1.1 修订:忽略 dsh 阶段实现资产**——领域层能力(探针取证/知识库/诊断 UI/验证管线)按新建规划(§11),Phase 0(dsh 原型)仅作验证证据与经验来源,不作复用输入。本文档需求按两层编号:领域层 **BR-xx**,平台层 **PLAT-xx**。模型接入基线:本地网关 OpenAI 兼容协议(Phase 0 以 deepseek-v4.1-flash 验证可行)。

### 2.3 领域覆盖范围

- **首发目标芯片**:STM32(Cortex-M)与 ESP32;KB 实际覆盖 18+ 家厂商(STM32 / GD32 / CH32 / ESP32 / ESP8266 / nRF5x / MSP430 / Tiva C / MSP432 / CC13xx-26xx / Kinetis / i.MX RT / SAMD / AVR / PIC32 / STM8 / EFM32-EFR32 / Renesas RA+RX / RP2040 / Nuvoton / WCH CH55x)。
- **症状域**:协议层(UART/I2C/SPI/CAN/USB/Modbus/LIN/Ethernet)、系统层(竞态/时钟树/中断/DMA/低功耗/看门狗/EMI/存储/ADC/电机/RTOS)、厂商独有陷阱、复合故障与间歇故障方法论。

## 3. 目标用户与使用场景

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| U1 嵌入式开发者(主) | 手上有板卡,报症状要根因 | 证据链完整、结论可证伪、少问废话(一次只问信息增益最大的问题) |
| U2 知识库维护者 | 审核 agent 沉淀、维护 KB 质量 | 沉淀有来源、门禁自动化、回归全绿 |
| U3 无人值守管线(夜批) | CI 式批量盲测 | 幂等、超时受控、exit code 可判、全程无人 |

> 当前为单人项目,三个角色由同一人承担;按角色分离表达需求,为未来扩展留接口。

典型场景:

- **S1 交互式诊断(真硬件)**:用户描述症状 → agent 分流提问 → 探针取证 → 根因 + 修复建议。
- **S2 交互式诊断(仿真)**:`sim-*` 目标自动路由 Renode,agent 走完同一流程(验证/教学/回归);故障注入是仿真独有强项。
- **S3 夜批盲测**:固定夹具 + headless 跑 agent → 记录判决与 KB 沉淀。
- **S4 知识运营**:agent/人发现 KB 缺口 → 贡献 inbox → 人工审核合并 → 回归。

## 5. 业务范围

### 5.1 范围内

- 症状驱动的诊断 agent(交互式 + headless);
- 探针/串口取证工具(真硬件 OpenOCD + 仿真 Renode)与诊断知识库及其运营;
- 无人值守盲测管线与质量门禁;
- 自研 agent harness(平台层,承载上述领域能力)。

### 5.2 范围外(冻结/明确不做)

| 项 | 状态 |
|---|---|
| LLM 直接控制仪器 | **永久禁止**(安全边界 R1) |
| 基于现成 harness(dsh 等)二次开发 | **排除**(方向变更 + v1.1 修订,自研) |
| 仪器侧 UI 与联动(LLM 提议/逐台人工设置) | 冻结存档(协议栈优先级已定:SCPI-over-LAN > Modbus-RTU-over-USB 串口 > SCPI-serial > USBTMC > GPIB 跳过),方向重启再启用 |
| 信号物理层诊断(振铃/串扰/EMI)、真实 USB 主机行为 | 只能真硬件,属人工执行域 |
| 向量 RAG | 未实测前不引入;判定标准已固化(rag-vs-agentic-search-todo.md §6) |
| 低优先级厂商补全 | Infineon XMC/TRAVEO、STM32WL/U5、Ambiq Apollo、音频蓝牙 SoC(物奇/恒玄/杰理)、ESP32-P4,按需 |

### 5.3 仿真边界(Renode 能验什么)

| 能力 | 仿真 | 真硬件 |
|---|---|---|
| 探针工具闭环(attach/halt/mem)、寄存器语义(RCC 复位值等)、UART 因果链(波特率/乱码/丢字节) | ✓(ELF 级确定) | ✓ |
| **故障注入(可控间歇/复合故障)** | ✓ 强项 | 难 |
| 信号物理层、真实 USB 主机行为 | ✗ | ✓ |

ESP32 仿真不用 Renode,用 Espressif QEMU fork(按需接)。

## 6. 领域层业务需求(BR)

### BR-1 症状驱动的根因诊断(核心)

- **需求描述**:用户报症状,agent 通过 KB 推理 + 工具取证,输出根因、证据链(寄存器值/反汇编/记账恒等式)与可证伪的修复建议(给出预测性观察,如"每次 printf 白等 100ms → LED 周期应为 600ms 而非 500ms")。
- **关键规则**:专家优先路由——确定性检查表置信度够直接答,新颖症状才交给 LLM 发挥;交互脚本一次只问一个信息增益最大的问题;置信度不足不硬答。
- **验收标准**:① KB 覆盖域内症状全部给出证据链支撑的根因;② 结论含可证伪预测;③ 新颖症状不编造,走澄清/沉淀路径。证据:r1-r10 十轮盲测全部给出寄存器/反汇编证据;3 真机案例出现超出 KB 文本的专家级推理。
- **来源**:work-summary §1.2、§3.2、§4.4。

### BR-2 证据取证(探针与串口,新建)

- **需求描述**:建设统一取证工具集,以 MCP 提供给 agent——探针类(设备枚举、attach/detach、halt/resume/reset、内存读写)与串口类(open/read/write/close/status);真硬件后端走 OpenOCD(子进程 + TCL 通道),仿真后端按目标自动路由 Renode(ELF 级确定性仿真),串口通道统一抽象(真串口 / 仿真 UART socket)。
- **关键规则**:读失败显式报错,不许把全 0 解码成"无故障";写内存/复位前先声明(R2);仿真边界不得当证据(如 Renode 未建模的 HFSR.FORCED 读 0 是仿真边界,不是"无故障"证据)。
- **验收标准**:① 全部取证工具在真硬件/仿真双后端闭环;② 机器硬约束满足——本机 pyOCD USB 枚举死锁,真硬件后端必须 OpenOCD;③ 仿真侧支持可控故障注入(间歇/复合故障);④ Phase 0 已验证此工具面设计可行(r1-r10 盲测 + 故障注入诊断闭环),新建按同等工具面实施。
- **来源**:work-summary §2.2、§4.1、§4.5(作为设计验证依据)。

### BR-3 诊断知识库与检索(新建 + 已有语料迁移)

- **需求描述**:建设分层知识库与检索入口,支撑三级渐进加载(目标结构,规模按 Phase 0 基准起步):

| 层 | Phase 0 基准规模 | 职责 |
|---|---|---|
| `vendor/` | 14 | 按厂商分流的症状诊断(覆盖 18+ 厂商) |
| `reference/` | 39 | 寄存器级查表,只查不推理 |
| `system/` | 15 | 竞态/时钟树/中断/DMA/低功耗/看门狗/EMI/存储/ADC/电机 |
| `protocols/` | 20 | UART×5 / I2C×4 / SPI×4 / CAN×2 / USB / Modbus / LIN / Ethernet / 传感器 |
| `debug/` `cases/` `method/` `rtos/` `rf/` | 13 | HardFault 解码 / 案例库 / 方法论 / RTOS / 射频功耗 |
| 索引 | 2 + index.yaml | 厂商分流总览 / 来源许可登记 / 症状索引(85 条目基准) |

  三层跳法:厂商分流索引(按厂商)→ 症状文件 → reference 查表。检索能力:`kb_lookup`(自然语言→索引 top-2)、`kb_read`(整文件读,路径限 KB 根内)、`kb_search`(精确 token:寄存器名/错误码/flag 名)。
- **关键规则**:症状文件必须四段式(完整 frontmatter / 第 0 步分流 / 症状→原因→测试表 / 交互脚本 / 常见陷阱),禁止"速查表"式;每次改 KB 必跑回归。载体形态依 harness 的 Skills 机制选型(决策点 #2),Phase 0 语料(103 文件,四段式 52/52 达标)经验证合格,直接迁移复用。
- **验收标准**:① 四段式达标 100%(以 Phase 0 的 52/52 为准入基线);② 回归双轨全绿(index 命中 case + search case,基准 172+102,随 KB 增长扩充);③ 检索层选型依 RAG 对照实验结论确定,上线主指标 Recall@2(见 §14)。
- **来源**:work-summary §3(语料与标准)、rag-vs-agentic-search-todo.md(检索选型)。

### BR-4 人机分工与安全边界

- **需求描述**:诊断过程中的动作按三类明确归属并在交互脚本中写明话术——**agent 自己做**(反汇编/读寄存器)、**问用户**(现象描述)、**建议用户执行**(仪器操作:逻辑分析仪/示波器/程控电源)。
- **关键规则**:R1 LLM 永不直接控制仪器;R2 写/复位前先声明;权限门禁需**工具类/参数级**粒度(mem_write 地址范围、serial_write 目标白名单、复位类操作可单独门禁)——依赖 PLAT-5。
- **验收标准**:① 全部症状文件交互脚本含三类动作归属;② 仪器操作仅以建议步骤形式出现,零违例;③ mem_write/复位类在权限层可被独立允许/拦截。
- **来源**:work-summary §1.3、framework-architecture-inventory.md §0。

### BR-5 知识沉淀闭环(新建)

- **需求描述**:建设沉淀通道——agent 诊断中发现 KB 未覆盖的坑/修正 → 沉淀工具写入待审 inbox → 人工审核合并 → 回归全绿。
- **关键规则**:来源许可(R7)——Apache-2.0/GFDL/CC-BY/CC-BY-SA 可直接收录并保留出处;无许可厂商内容只能改写附源 URL;自家实验标 `origin: 本机实测`。
- **验收标准**:① 沉淀通道自动化、审核人工化;② 沉淀合并后回归保持全绿;③ agent 诊断结论可纠正既有知识(Phase 0 已验证此闭环有效:夜批 10 轮沉淀 21 条,并出现过 agent 修正既有结论的案例)。
- **来源**:work-summary §2.3、§3.5、§4.4(作为设计验证依据)。

### BR-6 诊断过程可视化与会话回放(新建)

- **需求描述**:建设设备状态可视化——事件监听器捕获探针/串口工具结果,解析发布到前端状态,设备管理面板展示;**会话日志回放可复现**——重载页面显示上次扫描结果,不用重新查硬件。
- **关键规则**:回放依赖会话持久化(PLAT-2)与事件通道(PLAT-8);状态重建必须来自 transcript,而非重新查询硬件。
- **验收标准**:① 设备面板实时反映工具结果;② 页面重载后状态从会话日志完整重建;③ 实现形态依 harness 的 client 插件/前端扩展机制选型(Phase 0 已在 dsh client 插件机制上验证此交互模式可行,新建按同等体验实施)。
- **来源**:work-summary §2.4(交互模式验证)、framework-architecture-inventory.md #6/#13/#15、harness-comparison.md §4 #9(server-first 形态参照)。

### BR-7 无人值守验证管线(夜批盲测,新建)

- **需求描述**:建设自动化验证闭环——固件编译 → 夹具有界预检(防 hang)→ 起 headless agent 跑诊断 → exit code 携带结果 → 日志记录。夹具:仿真盲测(基准 10 例)+ 真机案例(基准 3 例)。
- **关键规则**:幂等(轮次标记);单轮超时上限(基准 25 分钟);headless 下 persona 指示"无人在场,自己用工具取证"。
- **验收标准**:① 全程无人值守;② 每轮产出寄存器/反汇编证据、根因判决与 KB 沉淀;③ 夹具防泄题(答案与案例目录分离);④ 依赖 PLAT-7 的 exit code/超时/事件流契约——Phase 0 已验证管线模式可行,但现有 harness 无整跑超时与完整 exit code 表,新框架需自补。
- **来源**:work-summary §4.2-§4.4(管线模式验证)、framework-architecture-inventory.md #16/#21、harness-comparison.md(各家 headless 能力对比)。

## 7. 平台层业务需求(PLAT)

> 全部为自研建设需求(全新开发,无现有 harness 可迁移);能力细目与优先级见 framework-architecture-inventory.md(P0 内核/P1 扩展安全/P2 交互自动化/P3 冻结),机制参照见 harness-comparison.md。此处只列业务级需求与验收方向。

| ID | 需求 | 业务理由 / 验收方向 |
|---|---|---|
| PLAT-1 | Agent 主循环 + 模型接入层:多 provider 统一适配(OpenAI 兼容/Anthropic 协议等)、流式、重试与超时、用量统计、模型降级 | 模型接入基线为本地网关 OpenAI 兼容协议(Phase 0 已验证),未来多模型并存。P0 |
| PLAT-2 | 会话管理与隔离:transcript 持久化、恢复/继续/派生、**会话间上下文与 MCP 连接隔离** | **用户点名硬需求**;BR-6 回放的依赖。P0 |
| PLAT-3 | 工具系统:注册与 Schema、执行器(超时/取消/大输出截断)、并行调用、错误结构化回传、最小内置工具集 | R3"工具必须诚实"落到框架——错误不许静默吞。P0 |

## 8. 硬性业务规则(不可妥协)

| # | 规则 | 来源 |
|---|---|---|
| R1 | LLM 永远不直接控制仪器(逻辑分析仪/示波器/程控电源),只提出操作步骤,人工执行 | 用户决定,最高优先级 |
| R2 | 探针写内存/复位前必须先声明(优先读) | persona 落实 |
| R3 | 工具必须诚实:读失败显式报错;全 0 不得解码成"无故障";错误结构化回传;仿真边界不得当证据 | 设计结论 6 + 实测教训 |
| R4 | 确定性事实进工具(寄存器位含义/错误码解码),因果推理进 KB + LLM | 设计结论 1 |
| R5 | 症状文件必须四段式,禁止"速查表"式;交互脚本必含三类动作归属(BR-4) | 质量门禁 |
| R6 | 改 KB 必跑回归(index 命中 + 精确 token 双轨,基准 172+102,随 KB 增长扩充),全绿才合入 | 质量门禁 |
| R7 | KB 收录遵守来源许可:可直接收录(Apache-2.0/GFDL/CC-BY/CC-BY-SA,保留出处);无许可厂商内容只改写并附源 URL;自家实验标 `origin: 本机实测` | 合规 |
| R8 | 质量缺口**一次修完**("不挤牙膏"):发现缺口先全量审计(结构完整性/触发词覆盖/回归),按清单一次修完,不等用户逐轮指出 | 工作方式沉淀 |
| R9 | 评测集构造规则先固化再生成,不偏袒任何被测方案 | 评测公正性 |

## 9. 主业务流程

### 9.1 交互式诊断(核心流程)

1. 用户报症状(自然语言);
2. 知识检索:自然语言症状 → 索引 top-2 候选;匹配不上 → 精确 token 检索(寄存器名/错误码/flag 名)(BR-3);
3. 读入症状文件 → 第 0 步分流(一个问题劈开假设空间);
4. 按"症状→原因→测试表"推进(按概率排序:原因 | 鉴别测试 | 预期观察 | 命中后动作)——一次只问一个问题,动作按三类归属(BR-4);
5. 探针/串口取证(内存读/串口读…)→ 证据与假设对表;
6. 输出:根因 + 证据链 + 可证伪修复建议(预测性观察);
7. KB 未覆盖 → 沉淀工具写入待审 inbox(BR-5)。

### 9.2 无人值守夜批(盲测)

固件编译 → 夹具有界预检(防 hang)→ 起 headless agent 跑诊断 → exit code 携带结果 → 日志记录。幂等,单轮 25 分钟上限(PLAT-7 契约)。盲测知识沉淀走 BR-5;出题答案与案例目录分离防泄题。

### 9.3 知识运营

发现缺口/修正(多来自盲测与日常诊断)→ 全量审计(交互脚本扫描 + frontmatter 完整性 + 回归)→ 按清单**一次修完**(R8)→ 回归全绿 → 合入。agent 贡献经待审 inbox 人工过目后合并(BR-5)。

## 14. 开放问题(进入 M1 设计前必须回答)

完整清单见 framework-architecture-inventory.md §3,此处列业务侧关切:

7. 多模型路由与降级;
8. MCP 连接生命周期(会话级 vs 全局级);
9. UI 形态优先级(CLI 先行 vs Web 先行;诊断 UI 需求 BR-6 为 Web 侧,倾向 Web 先行,形态学 opencode server-first);**已关闭(2026-10-19):Web 优先,不做 CLI**。M2 审批走 Web + HTTP API,headless 只保留库层策略;详见 [m2-roadmap.md](m2-roadmap.md)。
