## 控制器先做的一处：动作分类补全

`actions.ts` 里 71 个动作有 6 个**两边都不在**：`open` / `halt` / `evaluate` /
`trace` / `trace_set` / `window`。按「未知」处理会被 `diagnose` 直接拒绝——连开
个会话都做不到。

**没有**直接塞进 `DESTRUCTIVE_ACTIONS`。那个集合的契约是「每条都必须能给出
`declaration`」，由 `tools.test.ts` 的「每个破坏性动作都有写前声明」钉着；塞进去
那条测试立刻红（实测：`action open 缺少 declaration`）。

改为新增 `STATEFUL_ACTIONS`——「会改变状态、但没有写前声明语义」。对权限层它们与
破坏性同类（`diagnose` 下要审批），但不参与 declaration 检查。`meta` 里发的是两份
不相交的白名单，加起来覆盖全部 71 个动作。

## Round A 的三个任务

### Task 2 · MCP 工具按 action 判读写（`db6c929`）

**我独立复核了四条**（编译 `dist/` 后自己调，不读子代理的测试）：

| 验证 | 结果 |
|---|---|
| 不带白名单时有没有 `access` 属性 | `'access' in tool: false`，键序与改动前逐项相同 |
| 判定 | `registers → read`、`flash → write`、未知 → `unknown`、两边都在 → `unknown` |
| `diagnose` 端到端 | `registers → allow`、`flash → ask`、`nope → deny` |
| `read-only` | `registers → allow`、`flash → deny` |

**子代理主动上报的一条风险，我认同并记在这里**：`_meta` 是 MCP 客户端未校验的自由字段，任何 server 都能用这两份白名单影响自己的权限判定。方向上安全（白名单只能把动作从 `unknown` 提到 `read`/`write`，而 `unknown` 在三档预设下都是 deny），但确实把「某次调用是否免审批」的决定权部分交给了 server。要收紧就得由内核维护动作分类，属架构级改动。

### 我自己发现的一处回归（`77e2fb7`）

**Task 2 的改动有一个我没有预见到的副作用**：内核一旦看到**任一份**动作白名单就按动作判读写，而没被覆盖的动作是 `unknown`（`diagnose` 下 deny）。`serial` 是唯一只发 `destructiveActions`、不发 `readOnlyActions` 的 server。

我没有靠推理，编译 `dist/` 直接跑了对照：

| 动作 | 改造前 | 只发破坏性那份 | 补发后 |
|---|---|---|---|
| `read` / `ports` / `status` | `ask` | **`deny`** | `allow` |
| `write` / `open` / `close` | `ask` | `ask` | `ask` |

即：**读动作从「审批后可用」变成「不可能可用」**。修法是补发 `SERIAL_READONLY_ACTIONS`，并加一条测试钉住「两份白名单必须覆盖该 server 的全部动作，且互不相交」——撤掉补的那一行时 3 例红，实测过。

这条本该由内核侧的测试发现。Task 2 的测试只覆盖了「自带白名单的假工具」，没有覆盖「真实 server 发的白名单是否自洽」。教训：**改协议契约时，要有一个断言站在「所有实现方」那一侧**，不能只测被改的那一侧。

### Task 1 · 整镜像分段回读（`6319684`）

**我自己重写了夹具复核**（假会话 + 临时 `.hex`，与子代理的测试分开写）：

| 场景 | 结果 |
|---|---|
| 32 KiB 请求全量 | `segmented-full` / `segments=4` / 四次读地址 `0x8000000, 0x8002000, 0x8004000, 0x8006000` |
| 第 3 段坏一字节 | `ok=false` / `scope=spot` / 报的偏移 **`0x8004100`**（全局，不是段内） |
| 默认 64 字节 | `segments` 键**不存在**，返回形状与改动前相同 |
| 第 2 段读不回 | `scope=none` / `bytes=8192`（第 1 段的字节数）/ 说明第 2 段失败 |
| 预算 0 | 只读 1 段，`spot` |

**子代理指出的一处 brief 自相矛盾，它是对的**：brief 要求「既有 6 条测试一行不改」，但既有第 4 条断言的正是本任务要推翻的旧契约（「请求更大也只比 8192 并标 spot」）。两者不可能同时成立。它按 brief 的**目标**处理，改了那一条，其余 5 条原样未动。我复核后接受。

### 一处它指出、我确认后修掉的文档矛盾

三处文档仍在说「单次上限 8192 / 整镜像不校验」，而代码已经能整镜像校验。`README.md`、`docs/operations/keil-headless.md`、`mcp-servers/keil/README.md` 全部改掉，并把 `scope` 的四种取值写清（`spot` / `full` / `segmented-full` / `none`）。D-223 结案。

**一处保留的粗粒度**：`segments` 在段读失败时是「已发起」而不是「已成功」——第 2 段读不回时 `segments === 2` 但只成功 1 段。用 `segments × 0x2000` 反推覆盖量会算错，覆盖量要看 `bytes`。文档里写的是「看 `bytes`」，没有让人相乘。

### Task 3 · 领域小项四件（`50838fc`）

- `kb_search` 补 `count` / `truncated`。子代理指出一处我没想到的细节：`search()` 的遍历顺序不是 path 字典序，照抄 `grep` 的「保留先遇到的 N 条」会改变返回的是哪几条。它改成了**排序后保留最小的 limit 条**，行为与改动前一致。
- `serial` 补权限模板；`embedded` 模板把 `embed_pack` 改成 `embed_packs` 并补齐缺的 `embed_identify`。
- keil 错误码词表落地。子代理指出 brief 把 `keil_unsupported_action` 绑到 `UNSUPPORTED_ON_MDK_5_43` 是错的——那张表是 **UVSOCK 操作名**（`DBG_VTR_GET`、`PRJ_FLASH_ERASE`），不是工具 action，而且没有任何代码路径查它来做派发。它把码绑到了「未知 action」，并说明被表命中的两条路径各有更具体的码。这是对 brief 的正确纠正。

## Task 4 · 构建诊断结构化（`8cb385f`）

### 我为它写了两轮独立探针，第二轮找出两条窄处

第一轮用自己写的样本喂 `parseDiagnostics`（不读它的测试）：ARMCC 的
`error: #20`、ARMCLANG 的 `file:line:col`、链接级联折叠、噪声行、
正文引用 `file(line)` 不误判——都对。

第二轮专门找它的边界：

| 探针 | 结果 | 判定 |
|---|---|---|
| 两段式 `src/main.c:36:` | 正确解出 `file` / `line` / `code` | ok（子代理第一版在这里出过 bug，RED 里写着） |
| 三段式 `src/main.c:36:12:` | 正确取行号、不把列号当行号 | ok |
| **路径带空格** `..\My Project\main.c(36): error: #20: …` | **整行不识别** | 已知的窄，写台账 |
| **行号 0** `src/main.c:0: error: #20: …` | 退化成「无位置」的诊断，`code` 与 `message` 还在 | 已知的窄，写台账 |
| 行首有前缀词 `see src/main.c(36): error:` | 不识别 | 正确（否则正文引用会被当诊断） |
| warning 不作折叠依据 | 保留 2 条，折叠 0 | ok |
| 编译器 error 重复不折叠 | 保留 2 条，折叠 0 | ok |
| 链接错误排在编译器错误之前 | 不折叠 | ok（方向安全：少折不会误折） |
| 30 条 → 上限 20 | `total=30, entries=20`，尾部写明还剩 10 条 | ok |

两条窄处我**没有让它放宽**，而是写进了台账 D-200。理由：放宽第一条就要接受
「`see src/main.c(36): error:` 这类正文被误判」，在没有真实日志可验的前提下
不划算；第二条比整行丢掉好。

### 子代理主动上报的一条，我认为值得留着

`clean_rebuild` / `symbols` / `convert` 走 `keilCli`（`build/keil-build.log`），
**不经这个诊断**。brief 只点名 build/rebuild，所以它没照搬 D-200 原修复建议里的
`keilCli` 路径。这是一个仍然存在的缺口，已写进台账。

### 它主动收窄的一处判据，我复核后同意

brief 写「与前面某条 error 的消息重复」，最自然的宽读法是「符号名作为子串出现」。
它没用这条，而是要求**引号整名**。反例实测：`cannot open source input file "foo.h"`
含 `foo`，而 `foo` 同时是未定义符号——宽判据会把缺头文件静默折进缺符号里，
两个不同的问题合并成一个。我另跑了一遍，确认它保留了两条、折叠 0。
