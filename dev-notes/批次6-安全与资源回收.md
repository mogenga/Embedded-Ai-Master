## 前置：CI 红与「删掉」的判断

`42364168296` 的失败点只有一条：
`tests/check-ledger-status.test.ts:373` 断言 `readFileSync(台账).includes("\r\n")`。

**没有删 job，也没有删测试**，因为这不是环境问题：

- `.gitattributes` 写的是 `* text=auto eol=lf`，index 里那份台账是 LF。
- CI 全新检出 → 工作区 LF → 断言假。
- 本机 353 个文件是 CRLF（早于该属性、检出后没再重新检出）→ 断言真。

即「只在本机绿」的假测试，与 `9c2166e` 的 mock 判据问题同类。修法是把断言从
「工作区换行符」改成「真实台账解析出 20 条状态行」。CRLF 解析能力由同文件
第 201 行的合成用例（`join("\r\n")`）覆盖，那条不依赖磁盘状态。

**验证方式**（没有靠推理）：`.tmp/force-lf.mjs` 先备份再把台账写成 LF，
`npx vitest run tests/check-ledger-status.test.ts` → 26 passed；随后从备份还原。
推 `99a319f` 后 CI 两个 job 均 success（`42364809192`）。

## 预研：6.1 的代价与 6.3 的结构

### 6.1 的 taskkill 成本（实测，5 轮）

> **注意：这一节的探针结论后来被证伪了。** 我用的孙进程是**非 detached** 的，
> 而 Windows 上非 detached 后代本来就随父进程死（libuv 的 kill-on-close Job
> Object），所以「只等 spawn 就够」测的是一个恒真姿态。见文末「6.1 的最终结论」。


| 轮次 | `taskkill /T /F` 耗时 | 父存活 | 孙存活 |
|---|---:|---|---|
| 1 | 903 ms | 否 | 否 |
| 2 | 941 ms | 否 | 否 |
| 3 | 944 ms | 否 | 否 |
| 4 | 891 ms | 否 | 否 |
| 5 | 891 ms | 否 | 否 |

与 D-225 记载一致（500–850 ms，本轮机器 ~900 ms）。把它塞进 `close()` 就是每次
关闭多花 0.9 s，`mcp-manager.test.ts` 会从 ~26 s 涨到 ~49 s。

**子代理后续补充的实测**（它自己的探针，与我的结论相反）：taskkill 对**不存在的
pid** 也要 1.2–1.3 s，真正的「枚举子进程 + 终止」发生在约 1 s 处。把父进程在
spawn 后几十毫秒内收掉，`/T` 就找不到它的子进程了——它测出 0/10/25/50/100/200 ms
全部漏，250 ms 起稳定。最终实现取 `TREE_REAPER_HEAD_START_MS = 250`。

我的探针（`probe-order-real.mjs` 的 D 姿态）测出「等 spawn ≈8 ms 就够，3/3 全灭」。
**两边冲突，我没有强行裁决**：我的探针用 3 轮、父进程立即响应 stdin EOF（属于
优雅退出的有利情况），它的样本更多且覆盖了「父进程忽略 EOF」的最坏情况。实现
按它的 250 ms 落地，代价是每次关闭多 250 ms（而非 900 ms）。

### 6.3 的真实结构：两道 120s

| 位置 | 常量 | 缺省时 |
|---|---|---|
| `src/tools/pipeline.ts` | `DEFAULT_TIMEOUT_MS = 120_000` | 本轮没配 `timeoutMs` 就用它 |
| `src/mcp/manager.ts` | `MAX_CALL_TIMEOUT_MS = 120_000` | 硬顶，`mcp.json` 要得更多也没用 |

**管线层先触发**。它 abort → MCP 层收到 `outcome.kind === "aborted"` →
`beginDispose(state)` 把整台 server 的连接拆掉。所以模型看到的不是「构建超时」，
而是「MCP 连接断开」。

## 关键产出

### 6.1 正常关闭回收进程树（D-225）

`src/mcp/manager.ts` 新增 `reapProcessTree(pid, client)`：在收父进程**之前**起
`taskkill /pid <p> /T /F`，只等 250 ms 就交还给 SDK 关闭，**不等 taskkill 退出**。
未能确认回收时发 `dispose_incomplete` 状态事件（`McpStatusKind` 新成员），经
`toMcpStatusPayload` 进会话日志，桌面端渲染成一条 warn。

**POSIX 侧如实上报做不到**：`StdioClientTransport` 的 spawn 写死了
`shell:false, windowsHide`，**没有透传 `detached`**（`StdioServerParameters` 只有
`command/args/env/stderr/cwd/maxBufferSize`），所以父进程不是进程组组长，负 pid
不可用。实现在 POSIX 上返回「无法按组回收后代」，而不是假装成功。

### 6.1 的最终结论：我的探针错了，子代理对

子代理交回报告后，我独立复现了它的核心主张（`.tmp/probe-detached-verdict.mjs`，
只杀父进程、不碰孙进程）：

| 孙进程 detached | 存活轮数 |
|---|---|
| `false` | **0 / 4** |
| `true` | **4 / 4** |

**结论成立**：非 detached 的孙进程在 Windows 上本来就随父死。我先前三个探针
（`probe-taskkill-cost` / `probe-taskkill-ordering` / `probe-order-real`）测的
都是这个恒真姿态，因此「等 spawn 8 ms 就够」证明不了 taskkill 赢过竞速。

**真实时序**（子代理测出、我未重复测）：`taskkill /T /F` 从 spawn 到**真正开始
枚举**约 1 s（对不存在的 pid 也要 1.2–1.3 s —— 是进程启动 + 杀软扫描，不是遍历）；
而真实 MCP server 收到 stdin EOF 后 **0–109 ms 就退出**。所以对 detached 后代，
「起 taskkill → 等 spawn → 关父进程」结构性必输。实现取
`TREE_REAPER_HEAD_START_MS = 250`（detached 场景下 0/10/25/50/100/200 ms 全失败，
250 ms 起稳定）。

**我的教训**：造一个「证明 A 赢了 B」的探针之前，先证明**没有 A 时 B 会输**。
我漏了对照组，于是把「B 本来就会死」误读成「A 杀死了 B」。这是实验设计错误，
不是编码错误，而它差点让实现走错方向（如果按我的结论做，detached 后代永远收不到，
而我还会以为已经收干净了）。

**台账原文的因果也是错的**：D-225 写「先关 client 再 taskkill → 孙进程全部存活」
并归因于顺序。真正的变量是 detached。按 AGENTS.md 的规矩**不改原文**，在条目前
加了 2026-11-07 的复核注记说明这一点。

### 6.2 外链白名单与导航守卫（OPT-40）

新增 `desktop/link-policy.js`（纯函数，无 electron import，可单测）：

- 外链只放行 `http` / `https` 且 hostname 非空；`file` / `javascript` / `data` /
  `vbscript` / `ms-*` / `search-ms` / `smb` / `mailto` / `chrome` / `about` / 自定义
  scheme 全部拒绝。
- 判据用 `new URL().protocol`，**不是字符串前缀**：`HTTPS://` 会被前缀误杀，
  而 `java\nscript:` / `java\tscript:` / `\0javascript:` 解析后都是 `javascript:`。
- `will-navigate` 只放行「回到 index.html 自己」：`fileURLToPath` + `path.relative`，
  不用 `startsWith`（`index.html.evil`、`index.html/../x` 会混过去；Windows 上
  大小写不敏感）。
- `reveal-artifact` 拒绝空、相对路径、URL 串、含 `\0` 的输入。

**`setWindowOpenHandler` 选全拒绝**而非转 `openExternal`：本产品一窗一会话，
渲染器已有可见的链接点击路径，再路由一层会让同一手势按链接标记方式产生两种行为。
仓库里 `grep` 不到 `window.open` / `target="_blank"`，当前零影响。

**未做** `reveal-artifact` 的「必须落在会话 artifacts 目录内」：主进程不知道当前
会话 id，再推导一遍就是第二个事实源；正确位置是宿主把路径推给主进程。

### 6.3 长任务超时出口（OPT-13）

按用户选定方案：

- `MAX_CALL_TIMEOUT_MS` 120s → `600_000`，默认调用超时仍 `15_000`。
- `ToolDef` 新增 `callTimeoutMs`：`resolveTimeoutMs(opts.timeoutMs, callTimeoutMs?)`
  取两者较大者，**用户显式配的更优先**（工具声明只抬高地板）。
- `McpToolInfo` 新增 `callTimeoutMs`，`loadTools` 从收 `server: string` 改成收
  `config: McpServerConfig`（否则拿不到 `timeoutMs`）。
- `src/mcp/tools.ts` 把 `info.callTimeoutMs` 透传进 `ToolDef`。
- `src/corpus/seed.ts` 新增 `EMBEDDED_SERVER_TIMEOUT_MS`：keil `600_000`，其余 `120_000`。

**一个判断**：没给 `keil_debug` 单独声明 `callTimeoutMs`。它是**工具级**字段，而
该工具有 57 个动作——构建要 10 分钟、读寄存器几毫秒。给整个工具声明 600s 等于让
一次卡住的寄存器读取也占住会话十分钟。按用户选的「整台 server 共用一个上限」，
正确做法是改**种子配置里 keil 那一台**。

### 6.4 并发只读分支残留披露（OPT-34）

**任务书的前提不成立**。原验收写「超时后同批后续调用不再启动」，但并发分支里
所有调用在 `Promise.all` 那一刻**已全部启动**，没有「后续」可跳。

真正的问题：`executeAuthorized` 产出的 `pending` 在并发分支被**静默丢弃**。
改为用既有 `detail` 通道披露 `detail.mayStillBeRunning: true`（`shell` 的
`abortEscalated` / `terminateFailed` 是同一先例），不新增事件类型。串行屏障
逐字未动（diff 里 `waitForSettled|tool_skipped_after_timeout|settleGraceMs`
命中 **0** 次）。

另加一条钉子：`Promise.all` 的 reject **不会**取消兄弟调用——调用方拿到错误时
其他工具照跑。这是对当前语义的记录，不是修复。

`docs/BACKLOG.md` 的 6.4 验收已改写为披露口径。

### 6.5 权限层必须显式二选一（D-116）

`BatchOptions.permission` 原来可省略，省略即静默走无判定路径。改成类型上互斥的
联合：要么 `permission`（真判定并审计），要么 `unsafeSkipPermission: true`
（明确声明这批调用故意不经权限层）。类型层排除「两者都不给」，运行时另有
`assertPermissionLayerChoice` 兜住 JS 调用方与 `as unknown as`。`LoopCtx.permissionGate`
同一根因，一并改。

管线自身的并发/超时/落盘测试确实不需要权限层，因此改成显式
`unsafeSkipPermission: true`——把「这是故意的」写进代码，而不是掩盖。

### 6.6 审批摘要脱敏（D-113 / D-147）

`src/permissions/audit.ts` 新增三档判据：切词（驼峰 + 分隔符）后末词是计数名词
（`count`/`limit`/`length`/`size`…）→ **不脱敏**；任一词命中强敏感词
（`secret`/`password`/`credential`/`authorization`/`auth`/`apikey`/`private`/`cookie`）
→ 脱敏；末词命中弱敏感词（`key`/`token`/`session`）→ 脱敏。

标记格式 `[redacted:<类型>[:<规模>]]`，沿用本文件既有方括号约定
（`[non-finite:…]` / `[bigint:…]`）。**不保留前缀字符**——前几位往往正是密钥前缀
（`sk-`、`ghp_`）。`paramsDigest` 与 `paramsKeys` 未改；键名保留。

**主代理独立复核**（自己写探针，不看子代理测试）：真实工具面 31 个参数名
（`path`/`command`/`tokens`/`address`/`register_value`…）**误伤 0**；16 种应脱敏
拼写（`API_KEY`/`x-api-key`/`clientSecret`/`Set-Cookie`…）**漏网 0**。

**没做用户自定义敏感键**：`PermissionConfig` 走 `z.strictObject`，加字段要同时改
内核 schema、三层合并、`src/index.ts` 的校验、`writePermissionConfig`、桌面设置页
与宿主——而 `desktop/` 两个文件正是并行子代理的领地。少改任何一处，用户写进去的
字段都会判为未知字段、**整个会话启动失败**。已作为后续项记录。

## 被拒绝或纠偏的内容

- **没有删掉 CI 的 offline job**：失败原因是本机绿/CI 红的假测试，不是流水线本身
  有问题。删掉它等于把「构建能否通过、覆盖率闸门是否达标」一起放弃。
- **6.4 没有硬凑屏障**：并发分支没有「后续」可跳，加屏障只会得到不触发的死分支。
- **6.3 没有给 keil_debug 加工具级声明**：57 个动作共用一个预算会拖慢快动作。
- **6.6 没有做用户自定义词表**：跨任务改动，且少改一处会让会话启动失败。
- **6.2 没有把 window.open 路由到 openExternal**：会让同一手势产生两种行为。
- **6.1 没有在 POSIX 上假装成功**：SDK 不透传 `detached`，父进程不是进程组组长，
  如实返回「无法按组回收后代」。
