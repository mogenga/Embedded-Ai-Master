# M3 · 右侧面板串口助手（一期）

日期：2026-10-23。需求原话：「先转过头做右侧面板 顺便内嵌一个功能完善的串口助手 也方便agent直接读取 看看该如何实现 调研一下」→ 调研结论写入 `docs/serial-panel-spec.md`，用户答复「开工」。

## 关键决策

- **零 npm 依赖**：PowerShell .NET SerialPort 泵（调试 F429 时反复用它开 COM7，已验证），不走 node-serialport（native/ABI 风险 + AGENTS 依赖安装禁令）。
- **双通道不共口**：面板（host 进程）持口，agent（MCP server 进程）读镜像文件 `$HARNESS_HOME/serial/ring.json`（host 每次 flush 原子重写：tmp + rename）。COM 口独占语义靠镜像的 `ports[]` 判定，冲突时诚实报 `port_busy`。
- **内核零改动**：`serial_lines` 等事件由 host 直接产生，不进 transcript；agent 读取走 tool_result（evidence 白名单含 read/ports/status）。

## 实测钉死的坑（每一条都有复现证据）

1. **PS 事件是陷阱**：`Register-ObjectEvent -Action` 在主线程阻塞于 `[Console]::In.ReadLine()` 期间**永不执行**。复现：COM3 收到数据（轮询 P POLL 7×8），事件入队（EV fired 打印在退出时集中出现且 `$n` 为空），`eventsFired=0`。PowerShell 引擎只在空闲时跑 Action。
2. **`ReadLineAsync()` 同步阻塞**：等 stdin 的同时轮询串口的循环写法（`while (-not $task.IsCompleted) { Drain-Port }`）里内层循环 spin=0——它根本没跑。复现：probe3.ps1 计数。
3. **管道 stdin 的 `DataAvailable` 恒 false**（Node spawn 的 pipe）：`OpenStandardInput()` 同步读也不行，唯一通路是 `BeginRead` + 轮询 `IsCompleted`。且 **PS 函数内赋值是局部作用域**，跨调用状态必须 `$script:` 前缀，否则每次调用把 `$async` 重置为 null、BeginRead 永远重启、完成态丢失。复现：stdin-probe.ps1 两版对比。
4. **Console.Out 编码是 gb2312**：泵 Emit 中文行乱码（UTF-8 字节被 GBK 解码形态）。复现：`[Console]::OutputEncoding.WebName` = gb2312。泵开头 `[Console]::OutputEncoding/InputEncoding = UTF8`。
5. **SerialPort.Encoding 默认 us-ascii**：非 ASCII 打印成 `?`。open 前设 UTF8。
6. **session 对象缺字段**：`flushTimer: null` 漏写导致 debounce 永不建立（`undefined !== null`）——单元测试钉住。

## 双口互发实测（用户把两枚 CH340 交叉接好）

- 5 条消息（英文 / 中文 / warn / error / 9000 字符长行）全通；长行按 8192 截为 8192+808 两段；中文往返无损（修完编码后）；warn/error 自动分级进渲染层颜色；ring 500 行封顶、溢出计 `dropped`；mirror 落盘 `COM3(6)`。
- 宿主协议链路：`serialOpen` → `serial_snapshot` → `serial_lines`（150ms debounce 批量）→ `serialClose`；`listSerialPorts` 回 WMI 友好名（"USB-SERIAL CH340 (COM7)"）。
- 冲突路径：面板持有 COM3 时 `embed_serial read port=COM3` → `port_busy`（镜像判定）；transient 泵 open 失败也诚实报错。

## embed_serial（cubeide server）

动作面：`read`（无 port=读镜像；带 port+baud+duration_ms=一次性捕获 ≤30s）、`write`（一次性泵：写+监听回包窗口）、`ports`、`status`。泵脚本与 host 侧同协议但各自持有（host 是纯 ESM JS，dist-mcp 编译产物 import 不到；两份脚本头部注释互相指认）。

## 桌面实测与孤儿泵修复（22:43 用户实机点 Start 之后）

- 用户实机验证：**Start 成功**（泵起来了、没被杀软拦——D-206 在 Electron 主进程链下未触发，与预判一致）。
- **新坑实锤**：用户重启应用后 COM3 被占。追查：旧宿主的泵成了**孤儿**——Windows 上父进程死后子进程不自动退，泵攥着 COM3 到天荒地老。手动 `Stop-Process` 解围。
- **修复**（搜网确认是[社区标准模式](https://stackoverflow.com/questions/18983058)：父 PID 看门狗或 Job Object kill-on-close；后者需 native 调用不合零依赖）：泵主循环每 2s `Get-Process -Id $parent_pid`，宿主不在就 FlushLine + 关口 + exit；host 在配置行传 `parent_pid: process.pid`。实测孤儿泵 ~500ms 自退（orphan-test3.mjs）。stdin EOF 方案试过不可靠（父死后 BeginRead 不完成），已否决保留注释。
- 测试探针的教训：`Get-Process -Id X -ErrorAction Stop; exit` 的退出码经 execFileSync 判定会误报存活，改用 `Get-CimInstance Win32_Process -Filter "ProcessId=..."` 判 'ALIVE'/'DEAD'。

## 已知边界

- **D-206**：`node file.mjs` 进程链下杀软拦 `spawn powershell`（EPERM）；`-e` 与 Electron 主进程链不受影响。桌面实机待验。
- bridge 的 `close()` 最多等 2.5s 强杀 wedged 泵；open 有 8s ready 超时。
- 面板 500 行环 + agent 镜像同一份；`since` 游标按 ring index。
