## 预研：先量，再决定做不做

BACKLOG 里批次 7 的触发条件写得很清楚：「出现真实长会话、大日志或慢客户端反馈。
没有触发就不做」。所以我先写了 12 个探针脚本（全在 `%TEMP%` 下，不进仓库），
把六项各量一遍，再做范围决定。

### 量到的数

| 项 | 实测 | 结论 |
|---|---|---|
| `titleOf` 读整份日志 | 30 行首屏 × 0.5 MiB 日志 = **66–95 ms/次**；同一形状 5.13 MiB 真实日志整份读 10.0 ms，只读头 8 KiB **0.35 ms** | 真有问题：每次列表推送都付这个钱 |
| `sessions.list()` | 500 会话 **119–162 ms**，1000 会话 **226 ms**；stat×2 约是 read+parse 的一半 | 有代价，但本机真实会话数 **3**，触发条件不成立 |
| `grep` 全量收集 | 64 万命中 → **+112 MiB 堆**，每命中约 170 B | 真有问题 |
| `grep` 有界 top-N | 同语料堆增长约 **0**，输出逐条一致 | 可解 |
| `grep` ReDoS | `(a+)+$` / `(a\|a)+$` 对 **30 字符**输入 **>15 s**（子进程被 kill） | 真有问题，且是会话级卡死 |
| `glob` ReDoS | `**/a/`×12 组对 **32 段**路径 **>10 s**；×8 组 @48 段 >10 s；×6 组 @64 段 1.47 s | 真有问题：现有上限（256 字符 / 64 段）**拦不住** |
| 每事件 fsync | 现状 **2.41 ms/次**（append 1.16 + open/close 0.46 + sync 0.79）；真实会话每回合 **7–62 条事件** → 每回合 17–150 ms | 毫秒级，不值得拿断电保证去换 |
| `buildMessages` | @10000 事件 **2.8 ms**（中位） | 同上 |
| 内置工具 schema | 合计 **6.3 KiB ≈ 1616 token**；MCP 侧 description 合计约 1.6 K token | 不是瓶颈，且口径未定 |

### 一个决定性的技术验证：`vm` 能不能打断正则

D-085 的原修复建议是「`worker_threads`/子进程隔离」。我先验证了更轻的路子：

| 验证 | 结果 |
|---|---|
| `vm.Script#runInContext({ timeout: 300 })` 跑 `(a+)+$` | **309 ms 抛出 `ERR_SCRIPT_EXECUTION_TIMEOUT`**（不设 timeout 时 >15 s） |
| 被中断后同一 matcher 复用 | 正常返回，可以继续用 |
| 逐文件调用的固定开销 | 100 µs/次 → 2000 文件 **+550 ms（3×）** |
| 改为 50 文件一批 | 2000 文件只慢 **+35%**（239 → 322 ms） |
| 批内出现灾难性行 | **258 ms** 被打断，`code` 可辨识 |

结论：不需要 worker，`vm` 就够。按 50 文件/4 MiB 成批，超时预算 2000 ms/批。

## 设计取舍

**为什么 Task 3（glob）不跟 Task 2（grep）并行**：两者同属 `src/tools/`，且
`grep.ts` 依赖 `glob.ts` 的 `compileGlobMatcher`。批次 6 的教训是并发子代理在
同一工作区互相 `git reset`；这一轮除了拆开跑，还在 brief 里逐条禁止子代理做
任何 git 写操作。

**为什么 Task 1 只改 `desktop/host/host.js` 不改 `src/`**：桌面宿主已经加载
编译好的 `dist/`，改 `src/session/persistence.ts` 需要重编 `dist/` 才能生效；
而 `readSessionDir` 是公开 API，加「只读头部」的参数会牵动内核契约。标题推导
本来就是宿主层的展示逻辑，放在宿主里代价最小。

**为什么 7.1 只做 titleOf 不碰 `sessions.list()`**：本机真实会话数 3，
BACKLOG 的触发条件写的是「数百」。stat 缓存只带来约 2× 收益，属于有了数据再说的
一类。这一条写进台账，不是忘掉。
