## 工具 trace 为什么不做

我上一轮把它解释成「补一个耗时字段 + 一个按调用聚合的出口」，用户听完仍然不要。
这条决定成立的理由不是「它难」，而是**它的锚点已经有了替代**：

- 已有的 `tool_use` / `tool_result` 事件足以支撑转录与夜批判分（`requiredTools` 直接读 `tool_result.toolName`）；
- PLAT-8 给的价值是「夜批无人值守排障」，而夜批现在有 exit code 表 + 每轮的产物文件——挂了能看到哪条用例、哪个工具缺失、哪个关键词没命中；
- 真正剩下的增量只有「哪一步慢」，而耗时问题在毫秒级（批次 7 实测工具调用普遍 < 100 ms）。

**从批次 9 摘除，不留在排期里**。若将来夜批排障真的出现「不知道哪一步慢」的实测，
按 D-xxx 重新登记，而不是先写一个没人用的视图。

## 9.1 为什么只做离线部分

本机**没有 Renode**（`C:\Program Files\Renode\bin\Renode.exe` 不存在，PATH 里也没有），
现有 `scripts/diagnosis-e2e.mjs` 硬依赖它。但本地模型网关 `127.0.0.1:8788` 在监听。

所以管线做成**可注入后端**的形状：夹具描述期望的工具调用序列，模型由注入的
`fetchImpl` 提供。这样整条管线在没有硬件、没有网络的机器上能跑完、能判失败、
能验幂等与超时——这些正是 OPT-44 列的四项（夹具格式 + 幂等 + 整跑超时 + exit code 表）。
**真实 Renode 跑 10 条仿真用例**留给批次 10（需要环境）。

这一条要在交付里说清楚：**管线本身验证过，管线连真硬件没验证过。**
