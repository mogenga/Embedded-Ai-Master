## 工具 trace 到底是什么（写给下一轮决策）

**不是新建一套记录**。内核的会话日志里已经**有**每一次工具调用：

- `tool_use` 事件：`id` / `name` / `input`
- `tool_result` 事件：`ok` / `code` / `toolName` / `ts`

我在本机 3 个真实会话里核实过，一个会话 16 次调用、一个 10 次，逐条都在。

**缺的是两样**：

1. **每次调用自己的耗时**。日志里只有事件时间戳，两次相减能估，但**中间夹着模型的思考时间**，估出来的不是工具的真实耗时。要准确，得在管线里记 `startedAt` / `durationMs`。
2. **一个按调用聚合的出口**。现在要拼「这次调用是什么、花了多久、结果如何」得跨两三条日志行，没有一处能直接读。

价值锚点是 PLAT-8 写的「夜批无人值守排障」——夜批跑挂了要看哪一步慢、哪一步错。**不急**，但它不是仿 dsh。

## 9.1 为什么只做离线部分

本机**没有 Renode**（`C:\Program Files\Renode\bin\Renode.exe` 不存在，PATH 里也没有），
现有 `scripts/diagnosis-e2e.mjs` 硬依赖它。但本地模型网关 `127.0.0.1:8788` 在监听。

所以管线做成**可注入后端**的形状：夹具描述期望的工具调用序列，模型由注入的
`fetchImpl` 提供。这样整条管线在没有硬件、没有网络的机器上能跑完、能判失败、
能验幂等与超时——这些正是 OPT-44 列的四项（夹具格式 + 幂等 + 整跑超时 + exit code 表）。
**真实 Renode 跑 10 条仿真用例**留给批次 10（需要环境）。

这一条要在交付里说清楚：**管线本身验证过，管线连真硬件没验证过。**
