## 2026-10-25 · Windows 代码签名配置

### 关键产出

- `scripts/verify-signature.mjs` + `scripts/verify-signature.d.mts` —— 零依赖 PE 签名检查器，读 PE 头 Security Directory 的 Size 字段；退出码 0/1/2 可直接当发布门禁。纯函数导出（`isPeFile` / `readSecurityDirectory` / `inspectFile` / `parseArgs` / `formatResult`），CLI 入口在 `import.meta.url === pathToFileURL(...)` 判断里。

- `docs/deferred-issues.md` **D-211** —— 登记「配置就位但从未验证过真实签名」。

### 被拒绝或纠偏的内容

- **不写 `certificateFile` / `publisherName` 到仓库配置**。理由不是「怕泄露密码」那么窄：这些值因证书而异，写进仓库等于把「这台机器的证书」固化成项目配置，换人、换证书、换 CI 都要改代码。正确位置是环境变量 / CI secret。
- **不承诺「签了就没 SmartScreen 警告」**。新证书的信誉从零累积，OV 要数周至数月、EV 通常数天，且同样不是签完立刻生效。文档里明确写了这一条，避免对用户的错误承诺。
- **不用 `Get-AuthenticodeSignature` 作为验证主路径**。本机该 cmdlet 加载失败（`CouldNotAutoloadMatchingModule`，模块加载环境问题，非签名问题），实测复现。改用 Node 读 PE 头 + `signtool verify` 两条替代路径。
- **不启用 `forceCodeSigning`**。本机无证书，开启会让日常构建直接失败；文档里写明了它是让「签名静默跳过」无法被忽略的唯一开关，等证书就位再开。
- **不写 CI 配置**。仓库里没有 GitHub Actions workflow，本轮不新建；文档只用一句话说明「发布目前是本地手工执行」，并给出 CI secret 该放哪两个变量。
- **不动 `desktop/package.json` 的 `publish` 段**。该段由并行的另一个子代理添加（GitHub provider，owner `mogenga` / repo `Embedded-Ai-Master`）。本任务只加 `win.signtoolOptions`，两者互不覆盖。

### 翻车与返工

1. **Security Directory 偏移写错（真 bug，被自己的测试抓住）**。第一版 `readSecurityDirectory` 把安全目录项的偏移算成 `optionalHeaderOffset + dataDirectoryOffsetInOptional`，**漏了 `IMAGE_DIRECTORY_ENTRY_SECURITY * 8` 这一项**，等于永远在读数据目录的第 0 项（Export Table）的 Size。后果很隐蔽：真实未签名的 exe 上结果"恰好正确"（都是 0），只有手工构造的已签名 PE 会暴露。6 条测试红了才定位到，改成 `securityEntryOffsetInOptional = dataDirectoryOffsetInOptional + 4 * 8`。
   - **教训**：这个 bug 在「只测真实产物」的方案下**完全测不出来**——本机唯一的 exe 未签名，size 恒为 0，读错目录项也是 0。手工构造 PE 的测试不是形式主义，它是这个脚本唯一的正确性证据。

2. **测试断言过严**。`certificateTableWithinFile` 的用例断言 `fileSize > certificateTableOffset + size`，失败于 `1792 to be greater than 1792`。原因是构造的 PE 里证书表恰好**填满到文件尾**——而真实签名产物正是这种布局（证书表挂在文件末尾）。断言改成 `>=`，并在注释里写明理由。这是断言错，不是实现错。

3. **`--dir` 会不会触发 winCodeSign 下载**（父代理特别问的一点）。**不会。** 无证书时 `signFile` 在 `cscInfo == null` 处就 `return false`，`doSign` 未被调用，winCodeSign 工具链根本不需要。实测证据：两次 `--dir` 构建后 `%LOCALAPPDATA%\electron-builder\Cache` 里仍只有 09:11 那批 `7zip` / `nsis` / `nsis-resources`，**没有 winCodeSign 目录**，也没有新的下载时间戳。

4. **`signtool verify /pa` 在 git-bash 里会被 MSYS 路径转换搞坏**。直跑得到 `SignTool Error: File not found: D:/Git/pa` 与 `File not found: V:/`——`/pa` 和 `/v` 被当成了路径。加 `MSYS_NO_PATHCONV=1` 后正常。这条写进了文档 §6，因为它会让第一次用的人以为签名坏了。

5. **`--dir` 构建日志的误导性**。日志里有 `• signing with signtool.exe`，看起来像签过了。实际上 `windowsCodeSign.js:13` 在调用签名管理器之前无条件打印这行，真正的判断在后面：`no signing info identified, signing is skipped  signHook=false cscInfo=null`。用 `DEBUG=electron-builder` 才看得到那一行。产物 Security Directory size=0 才是事实。文档 §7 专门写了这一点。

6. **删产物影响了并行的发布子代理**。任务要求「跑完 `--dir` 把 `desktop/dist-installer/` 删掉」，我照做了；但同一时刻另一个子代理的 `scripts/release.mjs --check` 有一项是「安装包已产出」，我这一删使它的结果在两次运行之间从 OK 翻成 FAIL。两个子代理共享同一个 `dist-installer/` 目录，谁清理谁影响对方。不是缺陷，但并行派发时的协调盲点，已由对方在本文档同一文件的「GitHub Releases 部分」注明。

7. **最后一次 `--dir` 复跑撞上网络超时**（`connect ETIMEDOUT 20.205.243.166:443`，退出码 1）。Electron 44.9.1 的 zip 已在 `%LOCALAPPDATA%\electron\Cache` 里，但 electron-builder 仍会先发一次 HEAD 请求确认；那一次恰逢网络不通。**重试即成功**，配置未改一行。记在这里是因为它的表象容易误导：失败发生在 `packaging` 阶段、紧跟在 `packaging platform=win32 arch=x64` 之后，看起来像配置问题，实际与 `signtoolOptions` 无关（同一份配置此前此后各跑通一次）。

### 从源码读出的事实（不是猜的）

这几条都直接读了 `node_modules` 里的实现，因为它们决定了文档写什么：

1. **`--dir` 不产 `latest.yml`**。`latest.yml` 由 `NsisTarget` 的 `isWriteUpdateInfo: !this.isPortable` 触达 `PublishManager` → `updateInfoBuilder.writeUpdateInfoFiles`。`--dir` 的 target 不是 `nsis`/`nsis-*`，`isSuitableWindowsTarget()` 返回假，整个分支不执行。同理 `app-update.yml` 也不写（它由 `onAfterPack` 写，同样受该判断约束）。
2. **`--dir` 是验证 `publish` 配置的可行手段**，实测退出码 0、无 schema 报错。
3. **默认不上传**。`PublishManager` 构造里：`publishOptions.publish === undefined` 且无 CI/tag/`npm_lifecycle_event === "release"` 时，`publish` 保持 `undefined` → `this.isPublish === false` → `scheduleUpload` 不调，但 `createUpdateInfoTasks` 照跑，所以 `latest.yml` 照写。**三条隐式触发**（`npm run release` → `always`、CI tag → `onTag`、CI 环境 → `onTagOrDraft`）已写进 `docs/release.md` §5，因为将来加 CI 会让默认行为悄悄变掉。
4. **`releaseType: "release"` 是合法字段**（`GithubOptions.releaseType`，enum `draft|prerelease|release`，默认 `draft`）。父代理给的名字是对的。**但默认值是 `draft`**，所以显式写 `"release"` 意味着 `--publish always` 会直接公开发布，不是存成草稿——这一点在文档里点明了。
5. **`electron-builder` 不接受 version 带 `v`**。`gitHubPublisher.js` 里有 `if (version.startsWith("v")) throw new InvalidConfigurationError("Version must not start with v")`。所以 `checkVersion("v0.1.0")` 判 FAIL 不是风格偏好，是对着真实约束。`v` 前缀只属于 tag（`vPrefixedTagName` 默认 true）。

### 被拒绝或纠偏的内容

- **不接受「`gh` 未安装」这个前提**。父代理后来自己也纠正了。实现上做了双路探测：先试 `gh`，再试 `C:\Program Files\GitHub CLI\gh.exe` 等候选，还支持 `GH_EXE` 覆盖。找不到时报 FAIL 并给出路径线索，**不静默跳过**——`which gh` 为空就断言「未安装」是不诚实的（R3）。
- **不把 `--publish always` 当主路径**。理由写进文档：它把构建与发布合成一步（中途失败留半个 release），且完全不跑发布前检查。`gh` 那条可以先 `--check` 拦问题，也可加 `--verify-tag` 防 tag 指错提交。
- **不在 `release.mjs` 里执行任何 git / electron-builder / GitHub API**。父代理的要求，也是设计上的必要：发布不可逆，脚本的价值在「拦住坏包」和「把命令拼对」，不在「替人决定现在可以发」。
- **不在仓库里写任何 token**，包括示例值。文档和脚本输出里只有 `<your-gh-token>` 占位符。`pickAccount()` 还额外做了 token 擦除（`scrubTokens`），因为 `gh auth status` 的输出里有一行 `Token: github_pat_...`——虽然 gh 自己会打码，但打码实现可能变，多兜一层。

### 「方案说错的地方」——三条，都是读源码得到的

父代理要求明确指出方案里说错的地方。逐条如下：

1. **`gh` 未安装是错的**（父代理后来自己更正了）。实测 `/c/Program Files/GitHub CLI/gh.exe` 存在，v2.103.2，`gh auth status` 退出 0、账号 `mogenga`。只是不在 `PATH` 里。已改为双路探测。

2. **「加 `publish` 后 `--dir` 构建行为变了」——会变，但不是「生成 `latest.yml`」。** 实测 `--dir` 仍不产 `latest.yml`（它不是 NSIS 目标，`isSuitableWindowsTarget()` 为假），也仍不写 `resources/app-update.yml`（同一个判断）。**真正会变的是：完整 NSIS 打包时 `latest.yml` 的内容会带上 GitHub 改写过的文件名**（见下条）。另外 `--dir` 跑完后 `dist-installer/` 里除了 `win-unpacked/` 与 `builder-debug.yml` 什么都没有——这一点与加 `publish` 之前一致。

3. **最重要的一条：`latest.yml` 里的文件名会与磁盘上的不一致。** 这不是方案说错，是方案没提到的一个真实陷阱。链路：
   - 产物名 `Embedded AI Master Setup 0.1.0.exe` 含空格；
   - `platformPackager.js` 的 `isSafeGithubName` 只接受 `[0-9A-Za-z._-]`，于是 `computeSafeArtifactNameIfNeeded` 把空格换成 `-`；
   - `NsisTarget.js:303` 把它作为 `safeArtifactName` 传下去，`updateInfoBuilder.js:100-107` 在 `provider === "github"` 时把 `latest.yml` 的 `files[0].url` 与 `path` 都改成这个安全名；
   - 结果：`latest.yml` 写 `Embedded-AI-Master-Setup-0.1.0.exe`，磁盘上是 `Embedded AI Master Setup 0.1.0.exe`。
   - 走 `--publish always` 没事（`GitHubPublisher` 是 `super(context, true)`，上传名跟着改）；走 `gh release create` / 网页手动上传**就会对不上**，将来接 `electron-updater` 会去下一个不存在的资产。
   - 已加 `checkArtifactName` 检查项（报 WARN，因为这不是配置错误而是操作注意事项），并在 `docs/release.md` §2 末尾给出两条修法（上传前改名 / 改 `latest.yml`）。

   另外，`releaseType` 字段名是对的（`GithubOptions.releaseType`，enum `draft|prerelease|release`），父代理没写错。**但它的默认值是 `draft`**，所以显式写 `"release"` 意味着 `--publish always` 会直接公开、不存草稿——文档里点明了。

### 翻车与返工

1. **模板字符串里嵌了反引号，整份脚本解析失败**（`RolldownError: Cannot assign to this expression`）。`renderSteps()` 的返回模板里写了 `` `--check` ``——反引号提前闭合了模板。改成不加反引号。**教训**：这个脚本的正文就是一大段要打印给人看的 Markdown，和模板字符串语法天然冲突；写的时候要时刻记得正文里不能出现反引号与 `${`。
