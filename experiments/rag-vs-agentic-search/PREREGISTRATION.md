### 4bis. B 的预算修订（2026-10-20，因网关限流）

网关实测串行单线程、间隔 ≥ 15s、约 **4 次/分钟**；并发与突发成功率均为 0（详见 `STATUS.md`「M4 实测记录」）。原预注册的 `repeat: 3` 与网格 `{6, 12, 20}` 按此预算要 10 小时以上，不可行。修订为：

| 项 | 原值 | 修订后 | 耗时估计 |
|---|---|---|---|
| 重复次数 | 3 | **1** | 80 × 5–8 次调用 ≈ **1.7–2.7 小时** |
| 轮数网格 | `{6, 12, 20}`，全 dev 55 条 | **`{6, 12}`，10 条 dev 子样本** | 最坏 180 次调用 ≈ **45 分钟** |
| 稳定性测量 | 隐含于 repeat 3 | **独立跑**：10 条 dev 子样本 × 3 次 | ≈ **45–60 分钟** |

**代价与披露义务**：

1. 轮数在 **10 条子样本**上选，不是全 dev 55 条——报告中必须写「轮数在子样本上选，非全 dev」，不得含糊成「dev 上选出的」。
2. 正文 `repeat: 1`，**运行间波动未测**。补偿手段是上面第三行那条独立稳定性跑；报告须给出该跑的三次结果区间，并声明正文数字来自单次运行。
3. 网关的 `supports_seed: false`、temperature=0 三次三答（`STATUS.md` 有记录），所以"重复 1 次"的波动无法靠 seed 消除。这是端点的客观限制，不是设计选择。

### 4ter. B 轮数网格的子样本（固定，10 条）

**抽取规则**：在 dev 分区内**按 track 分层**，各轨取 `id` 字典序前 N 条；比例 34:21 ≈ 6:4，故取 index 6 条 + search 4 条。无随机性，与 seed 无关。

| 轨 | 查询 id |
|---|---|
| index（6 条） | `idx-001`、`idx-002`、`idx-003`、`idx-004`、`idx-006`、`idx-007` |
| search（4 条） | `srch-001`、`srch-002`、`srch-003`、`srch-004` |

> **为什么不取"前 10 条"**：dev 分区的 `id` 字典序前 10 条**全部是 index 轨**（`idx-001`…`idx-013`），一条 search 轨都没有。而 B 的 `grep` 工具恰好在精确 token 查询上最有价值——只用自然语言查询来调轮数，会让这个优势在网格选择阶段完全不可见。分层是对"子样本代表性"的必要修正，不是事后挑选。

**披露义务**：这 10 条参与了 B 的轮数选择，因此**不能**作为 B 在 dev 上的独立验证样本。报告中 B 的 dev 数字须分"含子样本 / 不含子样本"两列，或直接注明重叠。

### 4quater. B 的全量补跑（2026-10-21）

用户要求补跑 B 的全量 80 条。**这不改变预注册的参数选择**——`max_tool_rounds = 6` 仍由 §4ter 的 10 条子样本选出，全量跑批是**验证**而非调参。

| 项 | 值 |
|---|---|
| 样本 | 全量 80 条（dev 55 / test 25） |
| `max_tool_rounds` | 6（沿用 §4ter 的选择，未再调） |
| `repeat` | 1（同 §4bis） |
| 调用间隔 | 轮次内 ≥ 15s **且** 查询间 ≥ 15s |
| 结果 | 78 ok / 2 timeout / 0 error |
| 产出 | `results/runs/main/B.jsonl` |

**新增披露义务**：

1. **正文数字来自单次运行**，§4bis 第 2 条的稳定性补偿跑（10 条 × 3 次）**已于 2026-10-21 补跑**。
   区间：Recall@2 **[90%, 100%]**、Hit@1 **[80%, 90%]**、失败率 **[0%, 10%]**。
   逐条看有两条状态不一致且**失败的不是同一条**（`idx-006` 第 2 次超时、`idx-007` 第 3 次超时），
   两次都是「用满 6 轮未提交」而非网关错误。
   **但全量 80 条本身仍是单次运行的点估计**——稳定性只在 10 条子样本上量化过，
   把区间套到全量需要「子样本波动幅度代表全量」这一未经验证的假设。
   产物 `results/tables/stability_B.json`。
2. **两次跑批不在同一时间窗**（B 于 2026-10-21 跑，A/C/C′ 于 2026-10-20 跑），网关负载不同，绝对延迟不可跨方案直接相减比较。
3. **B 的 H7（负样本拒答）无法评估**：B 没有负样本跑批实现。**必须显式标「不报」，不得用「没人跑过」换来的 `no_match` 充当成绩**——上一轮就踩过这个坑（见 `docs/experiment-report.md` §5）。
4. **覆盖率分层敏感性分析现只覆盖 C vs C′**，「B 的优势是否部分来自评测集来源同源」这条威胁**未排除**。B 现在是结论里的最强方案，此项优先级高于其余未完成项。

### 4quinquies. 多 gold 补标（2026-10-21 已建）

spec §7.5 要求的增强项已补：**50 条 index 查询全覆盖**，38 条为多 gold，平均 1.94 个 gold/条。search 轨 30 条按 spec §7.5 未标（「精确 token 查询通常单 gold」）。

**标注口径**（供复核）：判定标准是「回答这条查询时，人会实际打开它」，
不是「主题相关」。据此**同协议的 `_overview.md`（速查表）不算**——
它是查参数用的，不是查症状用的。依据是各文件 frontmatter 的
`protocols`/`symptoms`/`domain` 声明与 `index.yaml` 的 `tags`/`summary`。

**影响范围**：**只影响 nDCG@5**。主判定指标（Recall@k / Hit@1 / MRR）
一律用原始单 gold（spec §7.3 第 5 条「主判定只用导入的原始 gold」）。
实测：接线前后 Recall@2 / Hit@1 / MRR **一个数字都没变**，
nDCG@5 因 IDCG 变大而全部下降，但**排序不变**（B > A > C′ > C）。

**残余偏差**：仍是**单标注者、无一致性系数**，故 nDCG@5 标低置信；
search 轨的 nDCG@5 仍是单 gold 口径。

## 6bis. 方案 C 的 dispatch 读法（**已选定：`deployed`**）

spec §8.4 的散文（「`kb_lookup` 存在关键词得分 > 0 的条目则取 top-2」）与 kb-mcp 实现（`lookup.found` 还需过置信度阈值 1.75、技术 token 覆盖度、中文覆盖度、OOV 折减）不一致。三种读法在 80 条查询上的 Recall@2：

| 读法 | 回退条件 | Recall@2 | lookup 分支 |
|---|---|---|---|
| (a) `deployed` | `lookup.found == false` 才回退 search | **0.4500** | 50 |
| (b) `lexical` | 无条目关键词得分 > 0 才回退（**不含 OOV 折减**） | 0.5375 | 67 |
| (c) `lookup_only` | 永不回退 | 0.4000 | 50 |

### 选定值与理由（2026-10-20）

**主口径 = (a) `deployed`**。理由不是它数字好看（它排第二），而是**它对应真实部署的系统**：(b) 要跳过 kb-mcp 实际存在的四道闸门、(c) 要删掉回退逻辑，二者都不是"现状基线"，而是构想出来的变体。方案 C 在本次实验中的角色是"现在的 kb-mcp 有多好"，改写它就不再回答这个问题。

**稳健性处理：三种读法全部报告。** 三者的实现都是纯本地计算，全报的边际成本约等于 0。因此本节同时预注册：

- 报告必须给出三种读法的 Recall@2 对照表，**不得只报 `deployed`**；
- 若三种读法下 C 与对照方案的**结论方向不一致**（例如在 `deployed` 下 C 劣于 C′、在 `lexical` 下 C 优于 C′），C 相关的判定一律写"**未决（口径敏感）**"，不得取其中一种作定论；
- 该对照表是**稳健性检查**，不是模型选择——不得事后改主口径。

### 两个必须随主口径一起披露的事实

1. **`deployed` 依赖一个未被强制的行为假设**：`kb_lookup` 的工具描述只要求「证据不足时如实告知」，**并未要求 agent 改调 `kb_search`**。因此 (a) 隐含「agent 见 `found=false` 就换工具」的假设；该假设不成立时 (a) 退化为 (c)，Recall@2 从 0.4500 掉到 0.4000。**本实验把该假设写进预注册，视为部署设计的一部分，而非实现细节。**
2. **`lexical` 若被引用，必须逐字写明"纯 keyword 得分，无折减、无覆盖度闸门、无阈值"**：实现时发现，若沿用 `lookup()` 内部的 OOV 折减再跳过阈值，同一查询会从 0.5375 掉到 0.4125——同一个名字能对应两种实现。本实验的 `lexical` 实现见 `schemes/kb_mcp.py::lexical_rank`，不含折减。
